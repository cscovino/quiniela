## 1. Diagnose Large Chunks

### 1.1 Investigate 353 KB i18n chunk

- Run `pnpm astro build --verbose` and check which modules end up in `i18n.*.js`
- Likely suspects:
  - `date-fns/locale/es` + `date-fns/locale/en-US` (used by `getRelativeTime` or similar in NavBar/translations)
  - Translation JSON files bundled into one chunk
- **Fix:**
  - If date-fns locales: replace `formatDistanceToNow` with `Intl.RelativeTimeFormat` (built into all modern browsers) OR lazy-import the locale only when needed
  - If JSON translations: ensure they're loaded as static strings, not bundled into a JS chunk

### 1.2 Investigate 182 KB client chunk

- Check what's in `client.*.js` — this is Astro's shared client entry
- Contains: `react`, `react-dom`, `firebase/*` (app, auth, firestore, app-check, messaging), `zustand`
- **Fix:**
  - Ensure `firebase/messaging` and `firebase/app-check` are lazy-imported (they already use `await import()` in firebase.ts, but verify tree-shaking works)
  - Check if `firebase/firestore` can be split from the main client chunk — pages that don't use Firestore (profile, login) shouldn't pay for it
  - Use `vite.build.rollupOptions.output.manualChunks` to split Firebase into its own chunk that only loads on pages that need it

## 2. Optimize Bundle Splitting

### 2.1 Configure manual chunks in `astro.config.ts`

```typescript
vite: {
  build: {
    rollupOptions: {
      output: {
        manualChunks(id) {
          if (id.includes('firebase/')) return 'firebase';
          if (id.includes('date-fns/')) return 'date-fns';
          if (id.includes('@i18n') || id.includes('/locales/')) return 'i18n-data';
        },
      },
    },
  },
},
```

### 2.2 Replace date-fns with native Intl

- Search for `formatDistanceToNow` or `date-fns` usage across the codebase
- Replace with `Intl.RelativeTimeFormat`:
  ```typescript
  const rtf = new Intl.RelativeTimeFormat(locale, { numeric: 'auto' });
  // e.g., rtf.format(-5, 'minute') → "hace 5 minutos"
  ```
- This eliminates the entire 353 KB i18n chunk

### 2.3 Lazy-load Firebase modules on non-Firebase pages

- Pages that DON'T need Firebase: home, tournament, rankings (static HTML)
- Pages that DO: predictions, profile, login, register
- Use React.lazy() or dynamic imports for Firebase-dependent components
- The 182 KB client chunk only loads on pages with interactive Firebase features

## 3. Consolidate React Islands

### 3.1 ToastProvider: inline in BaseLayout

- ToastProvider currently has `client:idle` — it's on every page but only activates on toast events
- Replace with a small `<script is:inline>` in BaseLayout that dynamically imports toast logic only when a toast event fires
- OR: keep as `client:load` but merge into NavBar's chunk (single island instead of two)

### 3.2 PWAInstall: keep lazy but optimize

- Currently `client:load` and only 1 KB — low priority
- Could be deferred to only load when `beforeinstallprompt` fires (change to event-driven)
- Low impact, can skip if time-constrained

### 3.3 NavBar: keep as `client:load` but audit its imports

- NavBar imports Firebase auth (for login/logout state) — this pulls in the Firebase SDK
- Verify it doesn't also import Firestore or messaging
- Ensure NavBar's Firebase usage is tree-shakeable (only `firebase/auth`, not the full SDK)

## 5. Enable Link Prefetching

### 5.1 Add `data-astro-prefetch` to NavBar links

```tsx
<a href={link.href} data-astro-prefetch>{link.label}</a>
```

This makes Astro prefetch the next page HTML on hover, eliminating the navigation delay.

### 5.2 Verify prefetch config in astro.config.ts

```typescript
prefetch: {
  prefetchAll: false,  // Only prefetch links with data-astro-prefetch
  defaultStrategy: 'hover',
},
```
